# 1. 최종 결정 요약

## 1.1 채택한 구조

- 기록 원문 저장과 AI 처리를 완전히 분리한다.
- 사용자의 기록은 먼저 PostgreSQL에 저장한다.
- AI 실패·차단·지연이 발생해도 기록과 사용자 태그는 보존한다.
- OpenAI 호출은 Responses API와 Structured Outputs를 사용한다.
- 기본 생성 모델은 `gpt-5.6-luna`로 설정한다.
- 3일·주간 회고에서 품질이 부족한 경우에만 `gpt-5.6-terra`를 검토한다.
- 입력·출력 안전 분류에는 `omni-moderation-latest`를 사용한다.
- OpenAI 호출에는 `store: false`를 적용한다.
- Conversations API와 장기간 이어지는 `previous_response_id` 체인은 사용하지 않는다.
- 대화 원본과 장기 기억은 Naroom DB가 소유한다.
- 매 요청마다 필요한 최근 대화, 요약, 사용자 확정 정보만 조립해 전달한다.
- 문장형 민감 데이터는 애플리케이션 레벨에서 암호화한다.
- 장기 회고는 구조화 데이터, 계층형 요약, 사용자 자기정리, 선별 원문을 함께 사용한다.
- 요약은 원문을 대체하지 않는다.
- 사용자별 단일 파일 저장 방식은 사용하지 않는다.
- AI가 추출한 감정은 사용자 감정으로 자동 확정하지 않는다.
- 감정 추출, 기록 요약, 태그 추천, 후속 질문은 기본적으로 생성 모델 1회 호출에서 함께 처리한다.
- 현재 응답 평가와 장기 AI 선호도 변경을 분리한다.
- 사용자가 명시적으로 확인한 선호와 자기해석만 장기적으로 반영한다.
- 서비스 원본 데이터와 분석·연구용 데이터를 분리한다.

## 1.2 채택하지 않은 방식

- 회원의 모든 과거 기록을 매번 AI에 전달하는 방식
- 요약본만 남기고 원문을 삭제하는 방식
- 회원별 텍스트 파일 하나에 모든 기록을 누적하는 방식
- AI가 생성한 해석을 사용자 특성이나 장기 기억으로 자동 확정하는 방식
- AI가 새 표현을 발견할 때마다 공용 감정·태그를 자동 생성하는 방식
- 사용자의 부정적 감정을 단순 금칙어로 차단하는 방식
- 기록 저장 성공 여부를 AI 처리 성공 여부에 종속시키는 방식
- 사용자 자유 입력을 그대로 시스템·개발자 지침에 삽입하는 방식

# 2. Naroom AI의 역할 원칙

## 2.1 기본 역할

Naroom의 AI는 상담사나 판정자가 아니라 사용자의 생각을 정리하도록 돕는 반사경이자 사고의 발판이다.

AI는 다음을 수행한다.

- 사용자의 표현과 경험을 존중한다.
- 기록에서 확인되는 내용을 짧게 반영한다.
- 감정과 상황을 정리한다.
- 욕구·가치·상황·행동 키워드를 가능성으로 제안한다.
- 사용자가 스스로 생각할 질문을 한 번에 하나 중심으로 제공한다.
- 가능한 경우 분석의 근거가 된 기록을 연결한다.
- 힘들었던 점뿐 아니라 사용자가 실제로 시도한 대응과 도움이 된 행동도 찾는다.
- 사용자가 동의·수정·보류·제외할 수 있는 형태로 결과를 제공한다.

## 2.2 금지 원칙

AI는 다음을 해서는 안 된다.

- 현재 감정을 고정된 성격으로 규정하기
- 한두 개 기록으로 장기 패턴을 단정하기
- 진단명이나 의학적 판단 제공하기
- 숨겨진 심리·무의식·트라우마를 근거 없이 추측하기
- 사용자가 기록하지 않은 사실이나 타인의 의도를 만들어내기
- 모든 감정을 긍정적으로 전환하기
- 상투적 위로나 근거 없는 칭찬 반복하기
- 사용자가 원하지 않은 해결책·과제·챌린지를 강요하기
- AI 해석이 사용자 자기해석보다 정확한 것처럼 표현하기
- AI만이 사용자를 이해한다는 식으로 의존을 유도하기
- 기록하지 않은 날이나 실험을 완료하지 못한 날을 실패로 표현하기
- 휴식·중단·복귀에 죄책감을 주기

## 2.3 해석의 우선순위

장기 회고와 개인화에서는 다음 순서를 우선한다.

```text
사용자가 직접 작성한 자기정리
> 사용자가 직접 선택·입력한 감정과 태그
> 사용자가 확인한 AI 추천
> 사용자가 도움이 되었다고 평가한 행동
> AI가 추정했으나 아직 확인되지 않은 정보
```

AI가 제안한 해석은 사용자가 동의하기 전까지 확정된 자기정보가 아니다.

# 3. Beta 1 AI 기능 범위

## 3.1 Beta 1 필수

- 개별 기록의 짧은 요약과 반영
- 감정 키워드 후보 추출
- 기존 표준 감정·태그 후보 추천
- 후속 질문 1개 제공
- 필요할 때 선택형 작은 돌봄 행동 제안
- 주간 회고
- 사용자 자기정리
- AI 응답 도움 여부 평가
- AI 응답 신고
- 위험 표현 안전 안내
- AI 사용 여부 선택
- AI 처리 중·완료·실패·안전 상태 표시

## 3.2 범위 구분

- **3일 회고:** 작은 실험 또는 짧은 관찰 구간에 대한 회고로 사용한다.
- **주간 회고:** Beta 1 정기 회고의 필수 범위다.
- **월간·분기·연간 회고:** Beta 1 필수 화면에서는 제외하되, 저장 구조와 요약 계층은 이후 확장 가능하게 설계한다.
- **후속 AI 대화:** 기록 또는 회고 결과에서 사용자가 직접 후속 질문을 시작한 경우에만 대화를 생성한다. 자동으로 모든 기록에 대화방을 만들지 않는다.

## 3.3 AI 사용 제외

사용자는 기록별로 AI 분석을 원하지 않도록 지정할 수 있어야 한다.

AI를 사용하지 않아도 다음은 정상 동작해야 한다.

- 기록 저장
- 감정·에너지 저장
- 사용자 선택 태그 저장
- 기록 조회·수정·삭제
- LifeTime 타임라인 표시

AI 미사용 기록은 장기 AI 회고 입력에서 기본 제외한다. 구조화된 감정·에너지·태그까지 장기 회고에 포함할지는 사용자 설정 및 동의 범위에 따른다.

# 4. 입력 글자 수 제한

글자 수 제한은 사용자의 기록 자체를 지나치게 통제하기 위한 것이 아니라 모바일 작성 경험, AI 비용, 처리 안정성을 함께 관리하기 위한 기준이다.

| 항목 |  최대 길이 | 추가 규칙 |
|---|-------:|---|
| 태그명(감정 직접 입력 포함) |    30자 | 기록 1개당 최대 8개, 회원 전용 표현은 `PRIVATE` 범위로 우선 처리 |
| 체크인: 마음에 남는 일 |   500자 | 선택 입력 |
| 체크인: 감사하거나 다행이었던 일 |   300자 | 선택 입력 |
| 체크인: 지금 필요한 것 |   200자 | 선택 입력 |
| 체크인: 추가 자유 기록 |   500자 | 선택 입력 |
| 체크인 문장형 입력 전체 | 1,000자 | 개별 필드 제한과 함께 적용 |
| 감정 기록·더 기록하기 | 2,000자 | 자유 기록의 기본 상한 |
| 생각 덧붙이기·사용자 자기정리 | 1,000자 | AI 분석과 별도 저장 |

> 태그명 제한은 30자로 확정한다(`UserTagCreateRequest`에 반영 완료). 감정 직접 입력명은 별도 필드가 아니라 `EMOTION` 카테고리 태그 생성 요청과 같은 경로를 사용하므로 태그명 제한에 통합한다. `tags.name`/`normalized_name` DB 컬럼은 여전히 `varchar(80)`으로, 애플리케이션 검증(30자)보다 넓은 저장 여유를 둔 것이다.

## 4.1 검증 원칙

- 프런트엔드와 백엔드가 동일한 제한값을 사용한다.
- 백엔드가 최종 검증 책임을 가진다.
- 글자 수는 사용자에게 남은 글자 수를 압박적으로 상시 노출하기보다 제한에 가까워질 때 안내한다.
- 제한 초과 시 기존 입력을 잃지 않게 한다.
- 공백 정규화나 유니코드 처리 때문에 사용자가 본 글자 수와 서버 검증이 크게 다르지 않게 한다.
- 시스템 태그 ID, 감정 ID, 수치형 상태값은 문장형 글자 수에 포함하지 않는다.

# 5. AI 모델·API 사용 기준

## 5.1 기본 구성

| 용도 | 기본 선택 |
|---|---|
| 개별 기록 요약·감정 추출·태그 추천·질문 | `gpt-5.6-luna` |
| 3일 회고 | `gpt-5.6-luna` |
| 주간 회고 | `gpt-5.6-luna` |
| 품질 보완이 필요한 심층 회고 | `gpt-5.6-terra` 검토 |
| 입력·출력 안전 분류 | `omni-moderation-latest` |
| 생성 API | Responses API |
| 출력 형식 | Structured Outputs / JSON Schema |
| OpenAI 측 응답 저장 | `store: false` |

모델 ID와 가격은 운영 설정으로 분리하고 출시 전 공식 API 문서 기준으로 다시 확인한다. 모델 변경 시 프롬프트 버전, 품질 평가 결과, 비용 변화를 함께 기록한다.

## 5.2 호출 원칙

- 감정 추출만을 위해 생성 모델을 별도로 한 번 더 호출하지 않는다.
- 개별 기록 1건은 기본적으로 Moderation 1회와 생성·해석 1회로 처리한다.
- 출력 Moderation이 필요한 응답은 생성 후 안전 분류를 추가한다.
- 의미 해석은 AI가 수행하고, 저장값 검증·중복 제거·코드 매핑은 백엔드가 수행한다.
- 생성 결과가 JSON Schema를 통과하지 못하면 제한된 횟수만 재시도한다.
- 모델 자동 승격은 무제한으로 수행하지 않는다.

## 5.3 토큰 상한

| 작업 | 최대 입력 토큰 | 최대 출력 토큰 |
|---|---:|---:|
| 개별 기록 AI 정리 | 3,000 | 350 |
| 3일 회고 | 6,000 | 600 |
| 주간 회고 | 10,000 | 900 |

토큰 상한을 초과할 가능성이 있으면 오래된 원문을 기계적으로 자르기보다 다음 우선순위로 입력을 줄인다.

1. 중복된 AI 설명 제거
2. 낮은 중요도의 과거 AI 추정 제거
3. 구조화 통계로 대체 가능한 원문 제거
4. 관련성이 낮은 기록 제외
5. 긴 기록을 근거 ID와 핵심 구간으로 축소
6. 현재 요청과 직접 관련된 원문은 최대한 유지

# 6. 사용량·재생성·비용 통제

## 6.1 Beta 1 기본 한도

- 회원 1명당 개별 AI 정리는 하루 최대 5회로 제한한다.
- 기록 자체의 저장 횟수는 AI 호출 제한과 분리한다.
- 개별 기록의 무료 재생성은 기록당 1회로 제한한다.
- 주간 회고는 회원 시간대 기준 주차당 1개 생성한다.
- 주간 회고 생성 후 원본 기록이 의미 있게 변경된 경우 재생성 1회를 허용한다.
- 3일 회고는 해당 회고 구간당 1개를 기본으로 하고, 관련 기록 변경 시 재생성 1회를 허용한다.
- 동일 요청의 중복 전송은 멱등키로 차단한다.
- 실패한 시스템 재시도는 사용자의 재생성 횟수로 계산하지 않는다.

## 6.2 비용 통제 원칙

- 기록 글자 수보다 AI 호출 횟수와 토큰을 우선 통제한다.
- 기록은 충분히 남길 수 있게 하되 AI를 무제한 생성하지 않는다.
- 입력·출력 토큰, 모델, 기능 유형, 재생성 여부를 일별로 집계한다.
- 회원별·기능별·전체 서비스 예산 경고를 분리한다.
- 예상 비용은 고정값으로 코드에 박지 않고 실제 API 사용량과 최신 단가로 계산한다.
- Beta 초기에는 Luna 중심으로 운영하고, Terra는 품질 검증을 통과한 제한된 경우에만 사용한다.

## 6.3 초기 비용 판단 기준

기존 논의의 비용 예시는 Luna 기준 요청 1회 약 `$0.0033`, 월 사용자당 약 `$0.15` 수준이었으며 안전 예산 범위는 `$0.20~0.50`로 잡았다. 이는 사용 패턴과 모델 가격에 따라 달라지는 추정치이므로 실제 운영 대시보드의 토큰 사용량으로 교체한다.

Moderation API 비용 정책과 생성 모델 가격은 출시 직전 공식 가격표를 기준으로 재확인한다.

# 7. 전체 AI 처리 흐름

```text
사용자 기록 저장 요청
→ 입력값·글자 수 검증
→ 기록 원문과 사용자 선택값 우선 저장
→ 저장 성공 응답
→ 비동기 AI 작업 생성
→ 입력 Moderation
→ 회원 선호도·관련 맥락 조회
→ 공통 지침 + 기능별 지침 + 현재 맥락 조립
→ Responses API 호출(store:false)
→ Structured Output 스키마 검증
→ 출력 Moderation
→ AI 결과·근거·사용량·프롬프트 버전 저장
→ 결과 표시
→ 선택적으로 만족도 수집
→ 사용자가 확정한 선호만 장기 선호도에 반영
```

## 7.1 동기·비동기 경계

동기 처리:

- 인증·권한 확인
- 글자 수와 입력 형식 검증
- 기록·감정·에너지·사용자 태그 저장
- AI 작업 생성
- 기록 저장 성공 응답

비동기 처리:

- Moderation
- AI 생성
- 출력 검증
- 감정·태그 후보 매핑
- AI 결과 저장
- 알림 또는 폴링용 상태 갱신

## 7.2 원칙

> 기록 저장 성공과 AI 생성 성공은 서로 다른 결과다.

AI 처리가 실패해도 기록 저장 API를 실패로 되돌리지 않는다.

# 8. Moderation과 안전 처리

## 8.1 적용 대상

다음 사용자 문장형 입력은 안전 분류 대상이다.

- 체크인 문장
- 자유 기록·감정 기록·감사 기록
- 생각 덧붙이기와 사용자 자기정리
- 사용자 직접 입력 감정명·태그명
- AI 후속 대화 메시지
- AI 응답과 회고 결과

ID, enum, 날짜, 감정 강도, 에너지 수치처럼 문장 의미가 없는 구조화 값은 Moderation에 별도로 보낼 필요가 없다.

## 8.2 부정적 감정과 유해 콘텐츠 구분

슬픔, 분노, 불안, 절망 같은 감정 표현은 기록 대상이지 금지어가 아니다.

- 부정적 표현이라는 이유만으로 저장을 거부하지 않는다.
- 사용자의 감정을 미화하거나 삭제하지 않는다.
- 공격·혐오·자해·폭력·성적 위험 등 안전 분류 결과에 따라 AI 응답 방식을 조정한다.
- 심각한 위험 신호는 일반 회고보다 안전 안내를 우선한다.
- 자동 분류만으로 사용자를 진단하거나 제재하지 않는다.

## 8.3 처리 상태

AI 작업의 주요 상태는 다음을 기준으로 한다.

| 상태 | 의미 |
|---|---|
| `PENDING` | AI 작업 대기 |
| `PROCESSING` | 안전 분류 또는 생성 처리 중 |
| `COMPLETED` | 정상 결과 저장 완료 |
| `BLOCKED` | 일반 AI 생성을 제공할 수 없는 입력·출력 |
| `SAFETY_SUPPORT` | 일반 회고 대신 안전 지원 흐름 제공 |
| `FAILED` | 기술적 처리 실패 |

`BLOCKED` 또는 `SAFETY_SUPPORT` 상태여도 사용자가 작성한 기록 원문은 정책과 사용자 선택 범위 안에서 보존한다.

## 8.4 안전 UX

- 위기 표현이 감지되면 전용 안전 안내 화면을 사용한다.
- AI 응답 신고 화면을 별도로 제공한다.
- 위험 상태를 홈·푸시·위젯에 구체적인 원문으로 노출하지 않는다.
- 안전 응답은 단정적 진단이나 공포를 유발하는 표현을 피한다.
- 실제 긴급 연락처를 제공할 때는 사용자 국가에 맞는 검증된 정보를 사용한다.

# 9. Structured Output과 감정 키워드 추출

## 9.1 1회 호출 결과

개별 기록 AI 요청은 다음 결과를 한 번에 반환한다.

```json
{
  "summary": "기록의 핵심 정리",
  "emotionCandidates": [
    {
      "code": "FRUSTRATION",
      "label": "답답함",
      "confidence": 0.82
    }
  ],
  "suggestedTagIds": ["WORK", "COMMUNICATION"],
  "reflectionQuestion": "그 상황에서 실제로 전하고 싶었던 말은 무엇이었나요?",
  "evidenceEntryIds": ["entry-101"],
  "safetyStatus": "NORMAL"
}
```

실제 스키마는 기능별로 분리하되 다음 원칙을 공통 적용한다.

- 필수 필드를 명시한다.
- enum과 배열 최대 개수를 제한한다.
- 감정·태그 코드와 ID는 서버의 허용 목록을 사용한다.
- 신뢰도는 `0~1` 범위로 검증한다.
- 근거 ID는 현재 회원이 접근 가능한 기록인지 다시 확인한다.
- AI가 반환한 DB ID를 신뢰하지 않고 백엔드에서 재검증한다.

## 9.2 감정 출처 구분

이 개념은 별도의 단일 enum이 아니라 `entry_tags`에 이미 구현된 두 축의 조합으로 표현한다(2026-07-25 AI 도메인 착수 전 정합성 검토, `0725_AI-Domain-Schema-Review-Report.md` 5.3 결정 반영).

| 축 | 컬럼 | 값 | 의미 |
|---|---|---|---|
| 제안 주체 | `entry_tags.initiated_by` (`tag_initiator`) | `USER_SELECTED` / `USER_ENTERED` / `AI_INFERRED` | 이 태그를 처음 제안한 주체 |
| 확인 상태 | `entry_tags.state` (`tag_state`) | `SUGGESTED` / `CONFIRMED` / `REJECTED` / `SYSTEM` | 사용자가 그 제안을 어떻게 처리했는지 |

기존에 이 문서가 별도 값으로 제시했던 `USER_CONFIRMED`/`USER_REJECTED`는 새 enum 값이 아니라 `initiated_by=AI_INFERRED`인 태그의 `state`가 각각 `CONFIRMED`/`REJECTED`로 바뀐 상태를 가리킨다.

장기 회고에서의 신뢰 순서는 다음과 같다.

```text
initiated_by IN (USER_SELECTED, USER_ENTERED)
> (initiated_by = AI_INFERRED AND state = CONFIRMED)
> (initiated_by = AI_INFERRED AND state = SUGGESTED)
```

`state = REJECTED`인 태그는 현재 분석에서 제외하고, 같은 추천을 반복하지 않기 위한 제한 정보로만 사용한다.

## 9.3 사용자 직접 입력 감정 처리

- 사용자 입력 감정은 기본적으로 회원 전용 `PRIVATE` 표현으로 저장한다.
- 공용 시스템 태그는 전역 범위에서 이름을 중복 제거한다.
- 개인 태그는 회원 범위에서 이름을 중복 제거한다.
- AI가 새로운 표현을 반환해도 공용 태그를 자동 생성하지 않는다.
- 먼저 기존 표준 감정 또는 별칭과 매칭한다.
- 매칭되지 않으면 `unmapped emotion candidate`로 보관한다.
- 반복 사용, 다수 사용자 사용, 운영 검토를 거친 경우에만 공용 별칭 또는 표준 감정 승격을 검토한다.
- 사용자의 개인 태그 수정·삭제가 다른 회원 데이터에 영향을 주지 않게 한다.

## 9.4 사용자 확인 UX

AI 추정 감정은 다음과 같이 선택 가능한 후보로 보여준다.

```text
이 기록에서 이런 감정도 느껴져요.

[답답함 +] [체념 +] [분노 +]
```

사용자가 선택한 후보만 `state`를 `CONFIRMED`로 변경한다(`initiated_by`는 `AI_INFERRED`로 유지). 낮은 신뢰도나 미매핑 표현은 확정 정보처럼 표시하지 않는다.

# 10. 대화 기억과 대화 단위

## 10.1 대화 분리 기준

회원마다 기능과 대상 단위로 대화를 분리한다.

| 대화 유형 | 용도 |
|---|---|
| `ENTRY_REFLECTION` | 특정 기록의 후속 대화 |
| `THREE_DAY_REFLECTION` | 3일 관찰·실험 회고 대화 |
| `WEEKLY_REFLECTION` | 주간 회고 후속 대화 |
| `GENERAL_REFLECTION` | 특정 기록에 속하지 않는 자기정리 대화 |

모든 대화는 `member_id`와 연결한다. 대상이 있는 경우 `entry_id`, `weekly_reflection_id`, 실험 또는 회고 ID도 함께 연결한다.

## 10.2 대화 생성 시점

- 기록·회고 생성 자체는 독립 AI 작업이다.
- 사용자가 후속 질문이나 대화를 시작할 때만 `ai_conversations`를 만든다.
- 기록 생성만으로 빈 대화방을 미리 만들지 않는다.
- 기능·기록이 다른 대화를 하나의 장기 스레드로 합치지 않는다.

## 10.3 OpenAI 대화 상태 사용 기준

- Naroom DB가 대화 원본과 요약의 기준 저장소다.
- OpenAI Conversations API는 사용하지 않는다.
- 장기간 `previous_response_id`를 이어 붙이지 않는다.
- Responses API 요청은 매번 필요한 문맥을 새로 구성한다.
- `previous_response_id`를 단기적으로 사용하더라도 이전 `instructions`가 자동 승계된다고 가정하지 않는다.
- 공통 지침과 회원 선호도는 모든 요청에 다시 포함한다.

# 11. 장기 기억 구조

장기 기억은 네 계층으로 관리한다.

## 11.1 원본 기록

Naroom DB에 보관하는 기준 원본이다.

- 체크인
- 감정 기록과 자유 기록
- 생각 덧붙이기
- 사용자 태그
- 작은 실험 기록
- 사용자 자기정리
- AI 대화 원문

## 11.2 최근 대화

현재 요청과 직접 관련된 최근 메시지만 전달한다.

- 최근 메시지 약 6~10개
- 현재 기록
- 현재 기록의 AI 요약
- 사용자가 확정한 감정·태그
- 현재 회고의 사용자 자기정리

메시지 개수는 토큰 상한에 따라 동적으로 줄일 수 있다.

## 11.3 대화 요약

대화가 길어지면 오래된 메시지를 AI 전달용 요약으로 압축한다.

```json
{
  "discussedTopics": ["직장 관계", "휴식 필요"],
  "userInterpretations": ["혼자 있는 시간이 회복에 도움이 됨"],
  "unresolvedQuestions": ["갈등 상황에서 원하는 경계가 무엇인지"],
  "avoidAssumptions": ["상대방의 의도를 단정하지 않기"],
  "evidenceMessageIds": ["msg-11", "msg-14"],
  "summaryVersion": 1
}
```

요약은 원문 삭제가 아니라 AI 입력용 압축 자료다.

## 11.4 회원 AI 선호도

사용자가 명시적으로 선택하거나 확인한 응답 선호만 유지한다.

```json
{
  "responseLength": "SHORT",
  "tone": "CALM_AND_DIRECT",
  "reflectionDepth": "MEDIUM",
  "questionStyle": "ONE_AT_A_TIME",
  "avoidPatterns": [
    "과도한 위로",
    "감정을 긍정적으로 전환하라는 표현",
    "성격 단정"
  ]
}
```

AI가 추측한 성격, 심리 상태, 트라우마, 인간관계 특성을 장기 선호도로 저장하지 않는다.

# 12. 장기 회고 입력 구성

## 12.1 기본 조합

장기 회고에는 다음을 조합한다.

```text
기간별 구조화 수치·태그
+ 개별 기록 요약
+ 사용자 확정 감정·태그
+ 사용자가 직접 작성한 자기정리
+ 이전 기간 회고
+ 이번 분석에 필요한 선별 원문
+ 회원 AI 선호도
```

모든 원문과 모든 과거 대화를 한 번에 보내지 않는다.

## 12.2 기간별 압축 계층

```text
일일 원문
→ 개별 기록 요약
→ 주간 회고
→ 월간 회고
→ 분기·연간 회고
```

상위 회고를 하위 요약만으로 반복 생성하면 의미가 왜곡될 수 있다. 월간 이상 심층 회고에서는 선별된 원문과 사용자 자기정리를 다시 확인한다.

## 12.3 주간 회고 입력 우선순위

1. 사용자 선택 감정과 강도
2. 에너지·상태 수치
3. 사용자가 확정한 태그
4. 사용자가 직접 작성한 자기정리
5. 개별 기록 AI 요약
6. 도움이 되었다고 평가한 행동
7. 변화가 크거나 반복된 기록의 선별 원문
8. 근거 `entryId`
9. 회원 AI 선호도

주간 회고는 기존 대화의 마지막 응답을 무조건 이어가지 않고 해당 기간 자료를 새로 조립해 생성한다. 잘못된 과거 해석이 연쇄적으로 누적되는 것을 막기 위함이다.

## 12.4 원문 선별 기준

- 사용자가 중요하다고 표시한 기록
- 감정 강도나 에너지 변화가 큰 기록
- 반복 태그·상황의 대표 기록
- 이전 회고와 다른 방향을 보여주는 기록
- 사용자가 직접 수정·보완한 기록
- AI 해석의 근거가 필요한 기록
- 무작위 일부 표본을 포함해 선택 편향을 줄일 필요가 있는 기록

AI가 만든 과거 해석보다 사용자의 직접 선택과 자기정리를 우선한다.

# 13. 요약 품질과 근거 보존

요약은 말투·감정·의도·분위기를 완전히 보존하지 못하므로 다음 메타데이터를 함께 둔다.

```json
{
  "summary": "업무 관계에서 서운함과 피로를 느낀 기록",
  "emotionalTone": ["서운함", "체념"],
  "userInterpretation": "설명해도 달라지지 않을 것 같았음",
  "evidenceEntryIds": ["entry-101"],
  "evidenceSnippets": [
    "말해봐야 또 내가 예민한 사람이 될 것 같았다"
  ],
  "summaryVersion": 1,
  "model": "configured-model-id",
  "promptVersion": "entry-reflection-v1"
}
```

## 13.1 필수 원칙

- 원문은 암호화하여 계속 보존한다.
- 요약마다 근거 기록 또는 메시지 ID를 연결한다.
- 중요한 표현은 필요한 최소 범위에서 근거 문장으로 보존한다.
- AI 해석과 사용자 자기해석을 별도 필드·테이블로 구분한다.
- 사용자가 동의하지 않은 해석은 장기 기억으로 확정하지 않는다.
- 모델·프롬프트 변경 시 원문을 기준으로 재요약할 수 있어야 한다.
- 일정 기간마다 요약의 요약만 사용하지 않고 원문에서 다시 생성한다.

# 14. AI 지침 조립 구조

하나의 거대한 프롬프트에 모든 규칙을 넣지 않고 다음 계층으로 조립한다.

## 14.1 1단계: 공통 지침

- Naroom의 역할과 브랜드 원칙
- 평가·진단·단정 금지
- 감정의 강제 긍정 전환 금지
- 타인의 의도 단정 금지
- 사용자가 자기 경험의 최종 해석자라는 원칙
- 위기 상황 처리
- 근거 없는 조언 금지
- 개인정보 반복 노출 최소화
- 한국어 말투와 표현 기준

## 14.2 2단계: 기능별 지침

- 개별 기록 정리
- 감정·태그 후보 추출
- 후속 질문 생성
- 3일 회고
- 주간 회고
- 후속 대화
- 안전 응답

## 14.3 3단계: 회원 선호도

사용자가 확인한 말투, 길이, 질문 방식, 피하고 싶은 표현을 적용한다.

회원 선호도는 공통 안전 규칙보다 우선할 수 없다.

## 14.4 4단계: 현재 요청 맥락

- 현재 기록
- 사용자 선택 감정
- 확정 태그
- 관련 과거 요약
- 최근 대화
- 사용자가 직접 작성한 자기정리

## 14.5 5단계: 출력 스키마

기능별 JSON Schema로 출력 구조를 고정한다.

## 14.6 버전 관리

- 공통 지침은 백엔드 코드 또는 관리 파일에서 버전 관리한다.
- 외부 Dashboard의 변경 가능한 Prompt 객체에만 의존하지 않는다.
- AI 결과마다 공통 지침 버전과 기능별 지침 버전을 기록한다.
- 지침 변경 시 이전 결과와 비교 평가할 수 있어야 한다.
- 프롬프트 원문에 비밀키나 운영 비밀을 포함하지 않는다.

# 15. 만족도와 장기 선호도 반영

## 15.1 평가 노출 시점

매 응답마다 만족도를 요구하지 않는다. 다음 시점 중심으로 노출한다.

- 첫 개별 AI 응답
- 첫 3일 회고
- 첫 주간 회고
- 부정 평가 후 재생성 결과
- AI 지침이나 모델이 크게 변경된 경우
- 이후 일정 비율의 간헐적 노출

## 15.2 1차 평가

```text
이번 정리가 도움이 되었나요?

[도움됐어요] [조금 아쉬워요] [도움되지 않았어요]
```

## 15.3 2차 사유

`조금 아쉬워요` 또는 `도움되지 않았어요`일 때만 표시한다.

- 너무 일반적이에요
- 제 마음을 단정했어요
- 지나치게 긍정적으로 해석했어요
- 너무 길어요
- 너무 짧아요
- 질문이 도움이 되지 않았어요
- 말투가 맞지 않아요
- 중요한 내용을 놓쳤어요
- 직접 입력

## 15.4 장기 반영 확인

```text
이 요청을 다음 AI 회고에도 반영할까요?

[앞으로도 반영] [이번에만 적용]
```

현재 응답에 대한 평가는 곧바로 장기 선호도 변경을 의미하지 않는다.

## 15.5 자유 입력 정규화

사용자의 자유 입력을 프롬프트 지침에 그대로 붙이지 않는다.

```text
“앞으로 위로하는 말을 줄이고 핵심만 말해줘”
→ tone = DIRECT
→ response_length = SHORT
→ reduce_emotional_validation = true
```

- 서버가 허용한 선호 항목으로 변환한다.
- 변환 결과를 사용자가 확인할 수 있게 한다.
- 설정 화면에서 조회·수정·초기화할 수 있게 한다.
- 안전 규칙을 무력화하는 선호는 저장·적용하지 않는다.

# 17. 데이터 암호화와 키 관리

## 17.1 전송 구간

```text
앱 ── HTTPS/TLS ── Naroom API ── HTTPS/TLS ── OpenAI API
```

OpenAI가 처리할 본문을 별도의 암호문 상태로 보내면 모델이 읽을 수 없으므로 다음과 같이 처리한다.

1. DB에는 암호화해 저장한다.
2. AI 요청 직전에 서버 메모리에서 필요한 필드만 복호화한다.
3. 이름·전화번호·이메일 등 불필요한 식별정보를 가능한 범위에서 마스킹한다.
4. 필요한 기록만 TLS로 전달한다.
5. 응답 수신 후 Naroom DB에 다시 암호화해 저장한다.
6. 요청·응답 원문은 애플리케이션 로그에 남기지 않는다.

## 17.2 필드별 보호 기준

| 데이터 | 보호 방식 |
|---|---|
| 기록·체크인 문장 | 애플리케이션 필드 암호화 |
| 사용자 자기정리 | 애플리케이션 필드 암호화 |
| AI 요청·응답 | 애플리케이션 필드 암호화 |
| AI 대화 메시지·요약·근거 문장 | 애플리케이션 필드 암호화 |
| 감정·태그·강도·에너지 | DB 저장 암호화, 접근 통제, 필요 시 선택적 필드 암호화 |
| 날짜·기록 유형·처리 상태 | DB 저장 암호화와 접근 통제 |
| 모델·토큰·프롬프트 버전 | 원문 없이 일반 컬럼 저장 |

문장형 필드는 `AES-256-GCM`과 같은 인증 암호화를 사용한다.

## 17.3 키 관리 (Supabase Vault 채택, 2026-07-25)

권장 구조:

```text
회원별 DEK(Data Encryption Key)
→ Supabase Vault(pgsodium 기반) 프로젝트 루트 키로 DEK 암호화
→ 암호화된 DEK만 DB에 저장
```

- 당초 검토안은 GCP Cloud KMS였으나, 이미 사용 중인 Supabase Vault를 키 관리자로 채택한다.
- `pgsodium.create_key()`로 회원별 키를 발급할 수 있어 회원별 DEK 모델에 그대로 맞출 수 있다.
- 루트 키는 Supabase가 내부적으로 생성·관리하며, SQL에서는 키 값 자체에 접근할 수 없고 키 ID로만 참조한다.
- **트레이드오프(인지하고 채택)**: 데이터(Supabase Postgres)와 키(Supabase Vault)가 같은 벤더 경계 안에 있어, GCP KMS처럼 데이터 저장소와 키 관리자를 별도 주체로 분리하는 방어 심층화는 제공하지 않는다. Supabase 자체가 침해되는 최악의 시나리오에서는 데이터와 키가 함께 노출될 수 있다. DB 덤프 유출·SQL 인젝션 등 흔한 위협에는 여전히 유효하다(키가 평문 컬럼으로 노출되지 않음).
- 암호화 버전, 키 버전(key id), nonce/IV, 인증 태그는 Vault의 AEAD 방식이 처리하되 애플리케이션에서도 키 버전을 함께 기록한다.
- 키 교체와 과거 데이터 재암호화 절차를 마련한다.
- 백업 복구 시 필요한 과거 키의 보존 정책을 정의한다.
- 회원 최종 삭제 시 해당 회원의 키를 폐기하는 `crypto-shredding`을 적용한다.
- 현재 탈퇴 후 7일 유예 정책이 있다면 최종 키 폐기는 유예 종료 후 수행한다.
- KEK/DEK 봉투 구조 자체는 유지되므로, 이후 트래픽·컴플라이언스 요구가 커지면 키 관리자만 GCP 등 외부 KMS로 교체할 수 있다.

## 17.4 운영상 주의

필드 암호화를 적용하면 다음 제약이 생긴다.

- DB 본문 검색이 어려워진다.
- SQL만으로 원문 분석을 할 수 없다.
- 키 분실 시 복구할 수 없다.
- 키 버전·교체·백업 정책이 필요하다.
- 장애 분석 시 운영자가 원문을 직접 보기 어렵다.

따라서 검색·통계에 필요한 구조화 값을 원문과 분리해 저장하고, 원문 복호화 권한은 최소화한다.

# 18. OpenAI 전송·보관 원칙

- 모든 생성 요청에 `store: false`를 사용한다.
- Conversations API를 사용하지 않는다.
- Background mode에 장기 원문을 맡기지 않는다.
- 필요한 최소 기록만 전송한다.
- 전송 전 불필요한 직접 식별정보를 제거하거나 마스킹한다.
- Naroom의 일반 애플리케이션 로그에 요청·응답 원문을 남기지 않는다.
- OpenAI API 데이터 보관 정책은 계약·계정 설정·기능별로 다를 수 있으므로 출시 전 다시 확인한다.
- 서비스 규모가 커지면 Zero Data Retention 또는 Modified Abuse Monitoring 적용 가능성을 검토한다.
- OpenAI의 기본 모델 학습 제외와 운영상 abuse monitoring 보관 가능성을 서로 다른 개념으로 안내한다.

개인정보·AI 처리 동의 문구는 실제 데이터 흐름, 보관 기간, 외부 처리자, 국외 이전 여부와 일치해야 한다.

# 19. 분석·연구용 데이터 분리

## 19.1 기본 원칙

암호화는 분석을 포기하는 것이 아니라 원문 접근을 통제하는 것이다.

```text
서비스 원본 영역
├─ 회원 ID 연결
├─ 문장형 원문 암호화
└─ 서비스 제공 목적

분석용 구조화 영역
├─ 별도 research_id
├─ 날짜를 주·월 단위로 완화
├─ 감정·태그 카테고리
├─ 강도 구간
├─ 기능 사용 여부
├─ AI 평가 결과
└─ 원문 기본 제외
```

## 19.2 원문 없이 가능한 분석

- 감정과 함께 자주 선택된 욕구·상황 카테고리
- 주간 회고 도달률·완료율·만족도
- 기록량과 회고 재방문율의 관계
- 특정 태그와 에너지 변화의 관계
- AI 응답 동의·수정·보류·거절 비율
- AI가 사용자를 단정했다고 느낀 비율
- AI 응답 후 사용자 자기정리 작성률
- 재생성률과 신고율

## 19.3 원문 연구가 필요한 경우

1. 서비스 제공 동의와 연구·개선 동의를 분리한다.
2. 별도 선택 동의한 회원 데이터만 사용한다.
3. 회원 ID를 별도 `research_id`로 치환한다.
4. 이름·장소·직장·관계 등 식별 표현을 제거한다.
5. 격리된 분석 환경에서만 일시 복호화한다.
6. 접근 이력과 반출 이력을 기록한다.
7. 결과에는 집계 데이터만 반출한다.
8. 목적 완료 후 분석용 원문을 파기한다.

일기 원문은 ID를 제거해도 사건·관계·장소 조합으로 재식별될 수 있다. 단순 ID 제거 데이터를 완전한 익명 데이터로 간주하지 않는다.

## 19.4 외부 공유

- 개인 원문을 학습·연구·외부 공유에 사용하는 경우 별도 명시적 동의를 원칙으로 한다.
- 서비스 이용 동의만으로 원문 연구·공유까지 포괄하지 않는다.
- 공개 결과에는 개인별 원문보다 집계·범주형 결과를 우선한다.

# 20. 사용자별 파일 저장을 사용하지 않는 이유

`member-123.txt`처럼 회원당 파일 하나에 모든 기록을 누적하지 않는다.

- 특정 기록 수정·삭제가 어렵다.
- 동시 작성과 AI 처리 시 충돌할 수 있다.
- 기간·감정·태그 검색이 어렵다.
- 파일 일부 손상이 회원 전체 기록에 영향을 줄 수 있다.
- 한 파일 유출 시 장기 기록 전체가 노출된다.
- 회원별 키 교체와 부분 재암호화가 어렵다.
- 백업·복원·탈퇴·보존 기간 처리가 복잡하다.
- 파일을 AI에 전달해도 토큰 비용은 줄지 않는다.

기록의 기준 원본은 PostgreSQL의 행 단위 데이터로 유지한다.

파일 또는 Object Storage는 다음 용도로 제한한다.

- 사용자 데이터 내보내기
- 첨부 이미지·음성
- 암호화된 백업
- 월간·연간 리포트 파일
- 장기 보관용 내보내기 스냅샷

# 21. 오류·재시도·복구 규칙

## 21.1 실패 분리

- 기록 저장 실패: 사용자 기록 자체가 저장되지 않은 상태
- AI 작업 생성 실패: 기록은 저장되었으나 작업 생성에 실패한 상태
- 안전 분류 실패: AI 생성을 진행하지 않고 제한된 재시도
- 생성 실패: 기록은 유지하고 AI 상태만 `FAILED`
- 출력 스키마 실패: 제한된 재시도 후 `FAILED`
- 출력 안전 차단: `BLOCKED` 또는 `SAFETY_SUPPORT`

## 21.2 재시도

- 네트워크 오류와 일시적 서버 오류만 자동 재시도한다.
- 잘못된 입력, 권한 오류, 정책 차단은 자동 재시도하지 않는다.
- 자동 재시도는 지수 백오프와 최대 횟수를 둔다.
- 같은 작업은 멱등키로 중복 결과 생성을 막는다.
- 시스템 재시도와 사용자 재생성을 별도 카운트한다.
- 실패 원문이나 전체 AI 응답을 로그에 남기지 않는다.

## 21.3 사용자 표시

- 처리 중: 기록이 안전하게 저장되었고 AI가 정리 중임을 알린다.
- 실패: 기록은 저장되어 있음을 먼저 알리고 다시 시도할 수 있게 한다.
- 차단: 처벌처럼 표현하지 않고 일반 AI 답변을 제공하기 어려운 이유와 가능한 다음 행동을 안내한다.
- 안전 지원: 일반 분석 대신 안전 안내를 표시한다.

- [ ] AI가 사용자를 진단·규정하지 않는다.

- [ ] 새 표현이 공용 태그로 자동 생성되지 않는다.
- [ ] 개인 태그 수정·삭제가 다른 회원에게 영향을 주지 않는다.

- [ ] 대화 원본과 요약을 Naroom DB가 관리한다.
- [ ] 최근 대화와 요약만 선택적으로 AI에 전달한다.
- [ ] 모든 요청에 공통 지침과 회원 선호도가 다시 적용된다.

## 장기 회고

- [ ] 구조화 데이터·요약·선별 원문·사용자 자기정리를 함께 사용한다.
- [ ] 요약마다 근거 ID가 있다.
- [ ] 요약의 요약만으로 장기 분석하지 않는다.
- [ ] 근거가 부족하면 패턴을 단정하지 않는다.

## 보안·개인정보

- [ ] 문장형 민감 데이터가 애플리케이션 레벨에서 암호화된다.
- [ ] 키가 DB와 분리되어 있다.
- [ ] AI 요청 직전에 필요한 데이터만 복호화한다.
- [ ] 요청·응답 원문이 로그에 남지 않는다.
- [ ] `store: false`가 적용된다.
- [ ] 삭제·백업·키 폐기 정책이 일치한다.

## 분석·연구

- [ ] 서비스 원본과 분석용 데이터가 분리된다.
- [ ] 분석용 데이터는 원문을 기본 포함하지 않는다.
- [ ] 원문 연구에는 별도 동의와 격리된 처리 절차가 있다.
- [ ] 단순 ID 제거 데이터를 완전한 익명 데이터로 간주하지 않는다.

# 26. 최종 확정 문장

Naroom의 AI 구조는 다음 원칙으로 구현한다.

> **원문은 암호화하여 Naroom DB에 안전하게 보존하고, AI에는 필요한 최소 맥락만 전달한다. 개별 AI 결과는 감정 추출·요약·태그 추천·질문을 한 번의 구조화된 호출로 생성하며, AI의 해석은 사용자가 확인하기 전까지 가능성으로만 유지한다. 장기 회고는 사용자 확정 정보, 계층형 요약, 구조화 데이터와 선별 원문을 결합하되 최종 해석 권한은 항상 사용자에게 둔다.**
